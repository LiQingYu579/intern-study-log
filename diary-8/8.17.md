## 绿盟 RSAS 漏洞扫描 API 学习

### 学习目标

结合绿盟 RSAS API 接口文档，学习漏洞扫描任务从“创建任务”到“获取扫描结果”的完整调用过程，重点理解后续“上线工单传入 IP → 自动触发漏洞扫描”这一需求在绿盟侧应该如何实现。


---

### 1. API 基础概念

首先学习了接口调用中几个最基础的概念：

- **URL**：接口访问地址，例如 `/api/task/vul/create` 表示创建漏洞扫描任务。
- **GET / POST**：
  - GET 主要用于查询数据，例如查询任务状态；
  - POST 主要用于提交数据或执行操作，例如创建扫描任务。
- **form-data**：接口提交参数的一种方式，可以理解为程序自动填写并提交一个表单。
- **JSON**：接口常用的返回数据格式，程序可以从中读取任务状态、任务 ID、扫描结果等信息。
- **HTTP 状态码**：
  - `200`：服务器正常响应；
  - `401`：认证失败；
  - `403`：没有权限；
  - `404`：接口不存在；
  - `405`：请求方式错误。
- **ret_code / ret_msg**：绿盟接口自己的业务返回结果，`ret_code = 0` 一般表示操作成功。

同时了解了 Username/Password 和 Basic Auth 等接口认证方式。

---

### 2. 创建漏洞扫描任务

重点学习接口：

`POST /api/task/vul/create`

创建任务时主要需要提供：

- `name`：扫描任务名称；
- `targets`：扫描目标，例如某个 IP、IP 范围或网段；
- `template_id`：扫描模板，可根据实际扫描策略选择。

例如工单中传入：

`10.1.130.253`

程序可以将该 IP 作为 `targets` 参数提交给绿盟，从而自动创建漏洞扫描任务。

扫描任务创建成功后，接口不会直接返回漏洞结果，而是返回一个：

`task_id`

可以把 `task_id` 理解成扫描任务的唯一“任务编号”，后面查询扫描状态和获取扫描结果都需要通过这个编号完成。

---

### 3. 理解异步任务

漏洞扫描不是一个立即完成的操作，可能需要几分钟甚至更长时间，因此不能在创建任务后直接等待结果。

完整逻辑是：

`创建扫描任务 → 获取 task_id → 查询任务状态 → 等待扫描完成 → 获取扫描结果`

这种“先创建任务，之后再根据任务 ID 查询状态和结果”的方式属于典型的**异步任务处理流程**。

这类设计不仅用于漏洞扫描，后续在文件处理、AI 任务、批处理任务等场景中也很常见。

---

### 4. 查询任务状态

重点学习接口：

`/api/task/status/{task_id}`

通过之前获得的 `task_id` 可以查询某个扫描任务当前执行到了什么阶段。

重点关注返回字段：

- `status`：任务当前状态；
- `process`：扫描进度，范围为 1～100；
- `status_info`：状态文字说明；
- `time_start_scan`：扫描开始时间；
- `time_end_scan`：扫描结束时间。

目前主要需要理解几个状态：

- `0`：等待扫描；
- `2`：正在扫描；
- `4`：扫描完成；
- `5`：扫描暂停；
- 其他异常状态：表示任务出现异常或停止。

其中最关键的是：

`status = 4`

表示扫描已经完成，可以继续获取扫描结果。

---

### 5. 轮询机制

由于任务不会立即完成，因此程序需要隔一段时间查询一次任务状态。

例如：

`查询状态 → 未完成 → 等待几秒 → 再查询 → 未完成 → 再等待 → 扫描完成`

这种不断按照固定时间间隔查询任务状态的方式叫做：

**Polling（轮询）**

例如以后可以每隔 5～10 秒查询一次扫描任务状态，而不是高频不断请求接口。

通过轮询，可以实现工单页面中的类似效果：

- 等待扫描
- 扫描中 35%
- 扫描中 78%
- 扫描完成

---

### 6. 获取扫描结果

重点学习接口：

`/api/report/task/{task_id}`

当任务状态变成扫描完成后，就可以根据 `task_id` 获取对应的漏洞扫描结果。

该接口还涉及：

- `page`：当前页；
- `page_size`：每页返回的数据数量。

这是因为一次扫描可能发现很多漏洞，接口不会一次返回全部数据，而是通过**分页**逐页获取。

后续拿到扫描结果后，可以进一步统计：

- 扫描到哪些 IP；
- 存在哪些漏洞；
- 高危、中危等风险数量；
- 是否存在影响上线的安全问题。

---

### 7. 任务控制相关接口

另外了解了扫描任务的控制能力，包括：

- **暂停任务**：`/api/task/pause/{task_id}`
- **继续任务**：`/api/task/resume/{task_id}`
- **停止任务**：`/api/task/stop/{task_id}`
- **删除任务**
- **任务列表**
- **正在运行任务列表**：`/api/task/active_list`

其中暂停、继续、停止等功能主要用于异常处理或人工控制。

对于第一版“上线前自动扫描”功能来说，最核心的仍然是：

`创建任务 → 查询状态 → 获取结果`

---

### 8. 认证扫描相关内容

初步了解了：

- 认证数据下发；
- 扫描登录认证。

这类功能可以为目标主机配置 SSH、SMB、RDP、HTTP/HTTPS 等登录信息，使扫描器能够登录目标系统进行更深入的检测。

目前上线工单自动扫描的第一版不一定需要认证扫描，因此这里只先了解概念，暂时不作为重点。

### 9. 与上线工单自动扫描需求的对应关系

结合老师提出的需求，目前已经可以梳理出基本流程：

```text
上线工单提交
    ↓
工单中获取待上线 IP
    ↓
调用绿盟创建漏洞扫描任务
    ↓
获取 task_id
    ↓
保存“工单 ID ↔ task_id”的对应关系
    ↓
定时查询扫描任务状态
    ↓
扫描完成
    ↓
调用接口获取扫描结果
    ↓
统计漏洞及风险情况
    ↓
将结果回写工单
```
