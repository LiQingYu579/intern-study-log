## 2. 使用环境变量管理配置

将原来写死在代码中的配置改为从环境变量读取，包括：

| 环境变量 | 用途 |
|---|---|
| `RSAS_BASE_URL` | 绿盟服务地址 |
| `RSAS_USERNAME` | 接口账号 |
| `RSAS_PASSWORD` | 接口密码 |
| `RSAS_TEMPLATE_ID` | 扫描模板 ID |
| `RSAS_REQUEST_TIMEOUT` | HTTP 请求超时时间 |
| `RSAS_VERIFY_SSL` | 是否验证 HTTPS 证书 |
| `RSAS_USE_MULTIPART` | 是否使用 multipart 表单 |

本地假绿盟配置示例：

```powershell
$env:RSAS_BASE_URL="http://127.0.0.1:8000"
$env:RSAS_TEMPLATE_ID="0"
$env:RSAS_USE_MULTIPART="false"
```

这样以后切换真实绿盟时，只需要修改环境配置，不需要修改代码，也避免将账号密码写进 Python 文件。

## 3. 使用 Session 和 Basic Auth

创建了统一的 HTTP 会话：

```python
RSAS_SESSION = requests.Session()
```

Session 可以统一保存：

- Basic Auth 认证
- 公共请求头
- HTTP 连接配置

配置账号密码后，创建任务、查询状态和获取结果都会自动携带认证信息，不需要每个请求重复配置。

## 4. 统一处理接口响应

新增了 `parse_rsas_response()`，统一执行：

```
检查HTTP状态码 → 解析JSON → 检查ret_code → 检查data字段 → 返回业务数据
```

创建任务、查询状态和获取结果三个接口现在共用同一套检查逻辑，减少了重复代码。

创建任务时还增加了 `task_id` 检查。即使 `ret_code=0`，如果没有返回 `task_id`，程序仍会判定任务创建异常。

## 5. 区分三种状态

进一步理解了接口调用中的三套状态：

| 状态层次 | 来源 | 示例 |
|---|---|---|
| HTTP 状态 | HTTP 协议 | 200、401、404、500 |
| 绿盟业务状态 | `ret_code` / `ret_msg` | 成功 / 失败及原因 |
| 扫描任务状态 | `status` 字段 | 正在扫描、扫描完成、异常停止 |

因此：

> **HTTP 200** ≠ **绿盟业务成功** ≠ **扫描任务已经完成**

程序必须分别判断。

## 6. 准备 multipart/form-data

当前假绿盟使用普通表单（`application/x-www-form-urlencoded`），真实绿盟文档要求创建任务时使用 `multipart/form-data`。

因此增加了 `RSAS_USE_MULTIPART` 开关：

- `false`：调用当前假绿盟
- `true`：按照真实绿盟文档发送 multipart 表单

目前客户端已经加入 multipart 请求能力，但假绿盟还不能解析该格式，因此暂时继续使用 `false`。这部分还不能算完成了真实绿盟接入。

## 7. 与工单需求的关系

今天改造的是系统中的绿盟适配层：

```
上线工单 → ticket_scan_service.py → rsas_client.py → 假绿盟或真实绿盟
```

工单服务只需要调用：

- `create_scan_task()`
- `get_task_status()`
- `get_scan_result()`

绿盟地址、认证、表单格式和错误处理都由 `rsas_client.py` 负责。
