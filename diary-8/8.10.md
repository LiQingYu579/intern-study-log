## 亿格云 AIDR — 企业 AI 安全治理平台 · 文档总结

### 一句话理解

这是一个专门管"企业里大家用 AI 工具安不安全"的平台。核心思路是：**以 AI 治理 AI**，让公司既能用上 AI 生产力，又不至于出安全问题。

### 为什么需要这个东西？

OpenClaw（一个 AI Agent 工具）火了之后，人人都开始在电脑上"养虾"（用 AI Agent）。但问题来了：

- 官方通报了 **82 个安全漏洞**（12 个超危、21 个高危）
- 全球 **7.2 万个实例**暴露在公网，默认配置很脆弱
- 员工私下用 AI 工具（叫"Shadow AI"），公司根本不知道谁在用、传了什么数据出去

### 平台叫 AIDR，管三件事

| 维度 | 意思 | 通俗说 |
|------|------|--------|
| **可感知** | 知道谁在用 AI、用了什么、传了什么数据 | "看得见" |
| **可管控** | 能拦截敏感操作、限制权限、阻断危险行为 | "管得住" |
| **可回溯** | 全链路日志，出了事能查到人、查到原因 | "查得到" |

### 具体管什么？四大块

#### 1. AI Agent 本身的安全

- 自动发现员工电脑上装了哪些 AI Agent（OpenClaw、QClaw 等）
- 审查配置：用了什么模型、连了什么地址、有没有对外暴露
- 1:1 还原 Agent 和用户的对话记录
- 运行时管控：拦截恶意命令执行、恶意外连、敏感文件读取

#### 2. Skill（技能/插件）安全 — 这块讲得最细

- 把 Skill 当成"高价值文件资产"来保护
- **能改吗？** → 只有管理员能改，Agent 只能读和用
- **谁读过？** → 每次调用都有审计记录
- **会被外发吗？** → 识别并通过脚本/Curl/网盘等途径把 Skill 内容传出去的行为，直接拦截
- 还能扫描 Skill 里有没有恶意代码、恶意提示词，基于云端情报发现"投毒"Skill

#### 3. 四个落地场景

- **员工用 AI**：发现 Shadow AI、检测提示词里的敏感内容、动态脱敏
- **AI 编程**：管 Copilot/Cursor 等工具，防止源代码和 API 密钥外传
- **AI Agent 操作**：监控 Agent 通过 MCP/Skills 执行的每一步操作，能拦截
- **AI 护栏**：给公司自建 AI 应用做输入输出防护，防提示词注入、过滤敏感输出

#### 4. 和现有安全体系联动

- 能跟 DLP（数据防泄漏）、EDR（终端检测）、工单系统打通，融入公司已有的安全运营流程

### 对产品的理解

- **这个产品踩的痛点很真实**：现在很多公司确实不知道员工在用什么 AI 工具、传了什么数据出去，Shadow AI 是个盲区
- **Skill 安全这块是亮点**：把 AI Agent 的插件/技能当成文件资产来保护（读写权限矩阵、外发检测），思路比较新颖
- **名字 AIDR**：对标 EDR（终端检测与响应）的概念——EDR 管终端安全，AIDR 管 AI Agent 安全
- **目前看起来偏概念/方案展示**：PPT 里没有具体的客户案例或数据指标，更多是讲"能做什么"而不是"已经做了什么"
- **和我们的关系**：亿格云是一个企业安全公司，AIDR 是他们面向 AI 时代的新产品线

## 实践对比：两院 Agent vs WorkBuddy

以上文档在看完后，感觉明白了一些，但是看完很快又没有记忆点了，接下来的工作增加了我的理解。

周末查看了智能创新中心第二季度工作汇报。

今天尝试使用了学院的 Agent 和 SKILL HUB，第一个是用于管理两院的智能体（OpenClaw/Hermes）；第二个是 WorkBuddy。

尝试让这两个 Agent 都使用 **smart-router** 对上面的文档进行总结，两院的智能体（OpenClaw/Hermes）做的又快又好，上面的文档总结就是它做出来的，符合我想要的文档要求，并且可以直接导出为 Markdown 格式。

WorkBuddy 做起来就难很多，在我给他 PPTX 文件后，它就会机械触发预设逻辑：有文件 → 必须调用文件解析 SDK → SDK 失败就装 Python 库重试，完全不会先判断"其实文本内容已经能读到，能不能直接总结"。

两个相对比，院内的智能体是经过场景调优的，会先做判断：工具走不通就立刻降级成纯文本处理。

而 WorkBuddy 的调度是硬规则：文件解析必须走工具链路，失败就反复重试，直到用户取消或报错，没有"走不通就换方案"的灵活度。这是客户端框架的硬伤，和模型、模式没关系。在我切换至提供的 GPT-5.5 后，可以完成任务，但是相较正常的 Agent，在 WorkBuddy 上可能会使用更多的上下文。对比下 Codex 同样的任务只使用约三分之一的 Token。

## 心得与启发

### 一、"笨"不是缺陷，是主动的安全设计选择

结合 WorkBuddy 和 AIDR 的心得，再回头看 AIDR 的设计理念，其实会发现很多之前觉得"反体验"的设计，背后都是企业级 AI 落地的必然逻辑。

之前觉得 WorkBuddy 死板、死磕工具、不会灵活降级，站在普通用户视角是体验差；但站在 AIDR 的治理视角看，这恰恰是企业级 Agent 的设计目标。

AIDR 的核心原则是「最小权限 + 白名单约束」，AI 的行为必须可预判、可干预，不能"自作主张"。

- 如果 Agent 太"机灵"，可以自己判断"这个工具不用了，我直接处理吧"，那它同样也可能自行判断"这个敏感文件我直接读了吧""这条命令我直接执行了吧"；
- 宁肯多绕几步、多试几次工具、显得笨一点，也绝对不能突破预设的权限边界，不能自己给自己"开绿灯"。

**启发：** 评价企业级 AI 产品，永远不能只用"聪不聪明、好不好用"这一个维度。用户体验的优先级，在企业场景里要让位于可控性、合规性、可审计性。"好用"是加分项，"可控"是准入项；没有安全边界的聪明，对企业来说是风险，不是价值。

### 二、AI 治理的本质，是给"看不见的生产力"套上缰绳

AIDR 反复强调「可感知、可管控、可追溯」，这三件事刚好对应了这几天接触的所有场景：

1. **可感知：消除 Shadow AI 盲区**
   我自己私下装 WorkBuddy、配置第三方中转 API、在 VS Code 里接 AI 插件，在公司视角里就是典型的"影子 AI"——不知道谁在用、接了什么模型、传了什么数据出去。
   AIDR 第一步做的就是资产发现：把所有终端上的 AI 客户端、插件、网页工具全部盘点出来，先从"看不见"变成"看得见"。

2. **可管控：给自动化行为踩刹车**
   我传一个 PPT，Agent 就自动调 SDK、装 Python 库、尝试执行命令，站在个人视角是"自动化"，站在企业视角就是风险敞口。
   AIDR 做的管控，就是给这些自动行为加规则：危险命令不许跑、敏感文件不许读、恶意域名不许连、Skill 不许随便改。不是不让 AI 干活，是让它在安全围栏里干活。

3. **可追溯：全链路责任闭环**
   我看中转后台只能看到"用了多少 Token、花了多少钱"，而企业级审计要还原的是：谁、在什么时候、用哪个 Agent、调用了什么工具、读取了什么文件、输出了什么内容。出了问题能定位到人、查到原因、闭环整改。

**启发：** AI 生产力越强，风险敞口就越大。治理从来不是为了限制 AI，而是让企业"敢用"AI。没有安全兜底的 AI 普及，就像没有刹车的汽车，跑得越快事故越严重。AIDR 这套体系，本质是给 AI 的创新速度装上了安全带。

### 三、Skill 不是插件，是 AI 时代的核心资产

PPT 里用很大篇幅讲 Skill 安全治理，把 Skill 当成「高价值文件资产」来保护，这个视角很有启发。

今天一直在接触 Skill、改模型配置、调工具调用，最开始可能觉得 Skill 就是"给 AI 加功能的小插件"；但站在企业视角，Skill 里沉淀的是：

- 内部业务流程、专属 Prompt、工作流模板
- 核心脚本、内部系统对接逻辑、数据接口规则
- 整个团队的 Know-how 和经验沉淀

所以 AIDR 给 Skill 定了非常清晰的权限矩阵：Agent 只能读和调用，默认禁止修改；写入、发布必须走审批；外发行为直接拦截。本质就是把 Skill 从"工具插件"，提升到了"企业数字资产"的保护级别。
