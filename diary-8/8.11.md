## 今日工作内容：绿盟扫描能力功能增强

今天研究如何在**绿盟现有漏洞扫描与代码审计系统的基础上做功能增强**。

前期和老师沟通时，了解到目前公司已经有较成熟的商业漏洞扫描器和代码审计产品，并且提供 API 接口，可以完成任务创建、自动扫描、结果获取等操作。因此目前的目标并不是重新开发一套漏洞扫描系统，而是考虑：

> **在现有绿盟扫描能力之后增加进一步的漏洞分析和结果优化能力。**

### 整体思路

```
绿盟现有扫描/代码审计系统
        ↓
产生原始漏洞扫描结果
        ↓
新增智能增强模块
        ↓
漏洞候选进一步分析
        ↓
补丁状态核验
        ↓
误报过滤 / 风险保留 / 人工复核
        ↓
输出增强后的扫描结果
```

### 绿盟系统和接口了解

今天进一步查看了绿盟 RSAS 系统以及相关接口文档，重点了解了：

- 扫描任务创建与执行
- 代码审计任务
- 任务状态查询
- 扫描结果获取
- JSON/XML 报告格式
- 漏洞名称、CVE、风险等级、漏洞位置和修复建议等信息

通过这些内容，初步确认后续可以通过 API 获取绿盟原始扫描结果，再把结果传入增加的分析模块中处理，而不需要修改绿盟扫描器本身的核心扫描逻辑。

### 功能增强方向确认

在确定方向时，没有直接使用之前自己的研究方法，而是先参考已有漏洞检测和漏洞复现研究，希望最终做出来的功能能够真正改善现有扫描结果。

目前重点关注的问题是：

> **扫描器发现疑似漏洞以后，如何进一步判断该代码是否实际上已经完成修复。**

因为实际测试发现，即使代码已经应用了安全补丁，一些漏洞检测方法仍然可能继续产生漏洞报警。

因此目前计划给绿盟现有扫描流程增加一个**后置补丁状态验证功能**：

```
绿盟扫描结果
      ↓
疑似漏洞 / CVE
      ↓
补丁状态验证
      ↓
仍存在漏洞 → 保留报警
已经修复   → 过滤或降级
证据不明确 → 人工复核
```

这样主要解决的是**扫描结果二次确认和误报压缩问题**。

## 技术验证与改进

为了验证这个思路，今天首先复现并测试了 MOVERY，用 Redis 不同版本进行实验。

MOVERY 可以根据历史漏洞特征发现代码中的相似漏洞函数，但测试中发现：

> 一些已经修复的代码仍然可能被识别为漏洞。

因此进一步加入了类似 FVF 的补丁验证思路，不只判断"像不像历史漏洞"，还判断当前代码是否已经具备官方补丁中的修复特征。

开始时使用 MOVERY 自带的补丁特征进行判断，但多个 CVE 的测试表明，部分补丁特征无法准确区分漏洞版本和修复版本。

之后改为分析**真实 Git 修复 Commit 和 Git Diff**，提取：

- 修复前的漏洞状态代码
- 修复后的补丁状态代码
- 真实修改涉及的函数和上下文

最终形成目前的双状态判断方式：

```
疑似漏洞函数
      ↓
漏洞态 Git 证据
      +
补丁态 Git 证据
      ↓
判断当前代码更接近哪一种状态
      ↓
KEEP / FILTER / REVIEW
```

其中：

- **KEEP**：仍具有漏洞状态特征，保留原扫描报警
- **FILTER**：具有较明确的补丁状态证据，可过滤疑似误报
- **REVIEW**：证据不足或存在冲突，交给人工进一步确认

## 当前功能定位

目前整个工作的定位已经比较明确：

> **不是替代绿盟现有漏洞扫描器，而是在绿盟完成第一次漏洞扫描以后增加一个智能结果增强模块。**

主要希望增强三个方面：

1. 对疑似漏洞进行二次核验
2. 识别 Similar-but-Patched 情况，减少误报
3. 对证据不足的漏洞自动标记为人工复核

后续如果效果稳定，可以通过绿盟现有 API 获取扫描结果，将这一模块接在现有扫描流程之后，从而形成：

```
绿盟扫描 + 漏洞结果智能分析 + 补丁状态核验 + 误报压缩
```

的增强流程。
